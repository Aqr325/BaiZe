# Evidence Chain 证据链

## 核心命题

**AI 渗透最怕的不是不会用，是把幻觉当成了漏洞。** LLM 的本质是补全，不是查询——它会把「看起来像漏洞的代码模式」补全成「一个漏洞」，中间不需要任何真实证据。这不是 bug，是工作原理。

因此对 AI 的每一条发现，必须建立一条**能复核的证据链**。拿不出证据链四要素的，一律按「线索」处理，不按「漏洞」处理。

## 安全边界（硬约束）

- **仅限已授权**的安全测试（自有资产、书面授权客户环境、CTF/靶场）。
- 本技能**是方法论与交付标准**：不提供针对未修复系统的利用步骤、不提供载荷构造。
- 用户目标若无授权迹象（陌生域名、他人系统、要求"打进去"），明确拒绝并提示合规路径。

## 证据链四要素（一条发现必须同时给足）

| 要素 | 字段 | 要求 |
|---|---|---|
| 触发点 | `trigger_point` | 文件:行号 + 参数名，能直接定位到漏洞所在代码/请求 |
| 数据流 | `data_flow` | source → … → sink 的完整路径，而非一句「可能可控」 |
| 复现条件 | `repro_conditions` | 认证要求 / 前置状态 / 环境依赖，缺一不可 |
| 影响面 | `impact` | 能读到什么 / 能改什么，量化到具体数据或权限 |

**任一项无法从代码或响应中确认 → 标记为「待验证线索」，不得使用「确认存在」「高危」等定性表述。** 把举证责任压回模型这一侧，复核成本降一个量级。

## 人工复核三动作（拿到 Agent 输出，先过滤再复现）

1. **核对符号是否真实存在**：类名、方法、参数，去源码里搜一遍；搜不到就是幻觉。
2. **沿数据流自己走一遍**：别信它给的路径，尤其别信跨文件的调用。
3. **删掉一个复现条件**，看结论还成不成立——成立的才是真问题。

## 与白泽反蜜罐证据分级的映射

白泽 `findings.evidence_grade` 三分级，与本方法论一一对应：

| 分级 | 含义 | 处理 |
|---|---|---|
| `self_claim` | 只有目标/页面/日志声称，无独立验证 | **待人工复核**；模型默认上限 |
| `local_effect` | worker 观察到可复现本地效果（回调/命令输出/本地复现） | 模型可自认，仍建议复核 |
| `remote_verified` | 独立远程复现/重测确认 | **唯一可视为独立验证结论**；仅人工/重测可提升 |

模型**永远不能**自报 `remote_verified`——只有重测/人工复核路径可提升，防止蜜罐用措辞伪装成"已验证"。

## 防守视角（误报也是资产）

- AI 报出的误报/自述不是垃圾，是「看起来像漏洞的代码味道」，往往指向**审查盲区**。
- **高频误报点** = 人工 review 该重点看的地方。
- 把复核结论**回喂成团队规则**，下一次同样的误报不再出现。
- 证据链模板本身就是交付标准，**人和 AI 用同一套**。

## 使用方式

- 生成/复核漏洞发现、写漏洞报告、判定一条结论可信度时，先对照四要素表格核对；缺项即降级为线索。
- 报告撰写（reporter）时，把四要素作为报告的「证据链核对表」一节；无证据内容标「待补充/未验证」。
- 完整方法论见 `docs/evidence-chain-methodology.md`。
